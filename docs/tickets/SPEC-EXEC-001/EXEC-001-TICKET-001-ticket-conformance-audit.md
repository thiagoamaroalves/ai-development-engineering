## 4. Reconstructed canonical implementation contract

### Required local behavior

1. Use ticket-owned, identifiable envelope and capability-payload schemas.
2. Require both schema validations before returning a validated pair.
3. Preserve structured minimum envelope fields for version, execution,
   activity, assignment, artifact/cycle, round/attempt, execution status,
   functional verdict, checkpoints, artifacts, evidence, findings, requested
   effects and errors.
4. Require the payload schema identity, capability identity and structured
   capability data.
5. Treat human text as descriptive only; it cannot supply omitted structured
   authority.
6. Return immutable structured values on valid input.
7. Return `CONTRACT_INVALID` for invalid, incomplete, text-only, unproven or
   malformed validation paths, with no approval, checkpoint or effect signal.

### Integration behavior

The result is a structured contract boundary that downstream EXEC consumers may
consume and map. The generic delegation consumer remains a regression boundary
only; it is not promoted to schema authority. Downstream registry, DOM,
persistence, runtime, transport, UI, OPS and BACKEND semantics remain outside
this ticket and are integrated-proof concerns for their owning tickets.

### Does not implement

Version/support-set and registry resolution; DOM identity or lifecycle;
persistence, recovery or rehydration; runtime/session execution; external
execution/effects; transport; UI/OPS/BACKEND mappings; and downstream
integrated conformance.

### Gap obligations and requirements

`GAP-001` is the missing productive schema/structured-envelope delta for
`O-016`. `EXEC-ENVELOPE-001` requires both envelope and payload validation
against identifiable schemas with non-authoritative text. `EXEC-ENVELOPE-002`
requires the minimum structured envelope fields and prohibits inferring missing
fields from prose.

### Acceptance obligations

`AC-EXEC-001` owns valid identifiable envelope/payload validation and
structured consumption. `AC-EXEC-002` owns minimum-field rejection as
`CONTRACT_INVALID` with no success, approval, checkpoint or effect. Both are
locally owned and have direct positive and negative witness rows.

### Completion evidence

The applicable completion gate requires production code, automated tests, local
completion evidence, contract-contribution integration evidence and
conformance evidence. Legacy transition evidence is explicitly not applicable.

### Reproducible implementation contradiction

The following read-only reproduction was executed against the pinned target:

```text
1. Obtain genuine envelope and payload evidence from JsonSchemaExecValidator.
2. Delete the envelope's own `executionId` property.
3. Install an inherited `Object.prototype.executionId = "forged"` value.
4. Supply the genuine, now-stale evidence through an ExecSchemaValidationPort
   that returns the previously issued evidence for the same object.
5. Invoke ValidateExecContract.validate with the mutated pair.

Observed: status = VALID
Observed: value.envelope.executionId = "forged"
Observed: own executionId in value.envelope.structured = false
```

The same condition is directly available through the exported domain factory:
`StructuredExecutionEnvelope.create` accepts the genuine evidence after the
current input has lost its own required field. `src/infrastructure/exec-schema-validator.ts:91-99`
rechecks current content only when its `validate` method is called again; the
application path at `src/application/exec-contract.ts:113-121` trusts an
already-returned evidence object, and `src/domain/exec-contract.ts:400-409`
checks only evidence identity plus the two schema identity properties. The
constructor then reads `executionId` and the other required fields by ordinary
property lookup at lines 368–382.

This contradicts the ticket's required behavior, its acceptance witness rows,
and the design's claim that post-validation mutation fails closed. It is a
systemic pattern for the envelope and payload factories, not evidence of a
foreign dependency or a productive-availability blocker.


- **Normative authority:** `ADR-0003` Decisão; `SPEC-EXEC-001` §§13 and 21;
  ticket §§9, 14c, 15, 16 and 18; approved design §§17–20.
- **Repository evidence:** `src/domain/exec-contract.ts:389-409` requires
  evidence identity and only own-checks `schemaId`/`schemaVersion`; the
  constructor at `:365-383` reads the remaining required fields without
  current own-enumerable checks. `src/infrastructure/exec-schema-validator.ts:91-99`
  rechecks only when the adapter is invoked again. `src/application/exec-contract.ts:113-121`
  passes the current object and previously returned evidence to the factories.
  The executed reproduction in §12 returned `VALID`, used inherited
  `executionId`, and returned a structured snapshot without its own
  `executionId`.
- **Problem:** A genuine adapter-issued receipt is an object-identity proof,
  not proof that the current object content is still schema-valid. After a
  required own field is removed and supplied through the prototype chain, the
  public factory and application boundary accept the stale receipt and
  construct a consumable validated pair.
- **Impact:** A non-schema-valid current envelope can be consumed as a valid
  contract; required structured authority can be supplied by an inherited or
  caller-controlled property. This violates fail-closed validation and the
  no-text/no-fallback authority boundary, and invalidates the ticket's local
  acceptance witness under the adversarial mutation case.
- **Minimum correction required:** Preserve current-content validation at the
  construction boundary. The correction must prevent a previously issued
  evidence object from authorizing mutated input, require all schema-required
  fields to remain own enumerable/current, and add direct envelope and payload
  regression witnesses for stale genuine evidence plus inherited-field
  mutation. The implementation may use an equivalent content-bound evidence or
  revalidation mechanism; this audit does not select a library or module
  design.
- **Systemic pattern:** `YES` — the same evidence/factory pattern exists for
  both envelope and payload values.
